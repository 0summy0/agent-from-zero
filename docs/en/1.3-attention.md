# 1.3 Context Windows and Attention: From Dot Products to Weighted Mixing

## 1. What this chapter tackles

How can a model tell which tokens in the current window are most relevant when processing another token? This chapter implements a tiny scaled dot-product attention calculation step by step using five hand-built vectors. It uses only the Python standard library and a CPU, with no GPU, network, model weights, or API key.

The toy sequence `I like small models too` is only easy to inspect; it is not a complete model of language. Each token has a two-dimensional query, key, and value vector.

## 2. What query, key, and value do

Think of one attention calculation as “ask, match, retrieve”:

- The query is the current token's question: what information am I looking for?
- The key is a candidate token's index: which questions does this information suit?
- The value is a candidate token's content: what can I contribute after a match?

The current query takes a dot product with every key. A higher score means a stronger match. Softmax turns the scores into attention weights that sum to 1, and a weighted sum of the values produces the current token's context vector.

```text
score_j = dot(query, key_j) / sqrt(d_k)
weight_j = exp(score_j) / sum(exp(scores))
context = sum(weight_j * value_j)
```

Here `d_k` is the key-vector dimension. The values in each dimension are small in this example, so scaling does not make the weights extreme; its purpose is easier to observe with larger values in higher dimensions.

## 3. Why divide by the square root of d_k

A dot product multiplies and adds across dimensions. If the dimensions are roughly independent with unit variance, the dot-product variance is also about `d_k`. As dimensionality grows, scores can become large, softmax may concentrate on only a few candidates, and gradients can shrink.

Dividing by `sqrt(d_k)` keeps the score scale more stable. It does not change the ranking produced by the dot products, nor does it turn softmax weights into zero-sum scores.

The implementation subtracts the largest score before exponentiation: `exp(score - max)`. This numerical-stability trick preserves the final softmax result while avoiding overflow in `exp`.

## 4. Run the complete example

From the repository root, run:

```bash
uv run python chapters/stage1-how-lm-works/attention.py
```

The output has `full_window` and `context_window` sections. The first keeps all five tokens; the second keeps only the three most recent. Each row shows the query token, scaled dot-product scores, attention weights, and context vector. The `keys` and `values` fields list the content searched and mixed in that window.

You can inspect the complete output structure with the standard library:

```python
import runpy

chapter = runpy.run_path("chapters/stage1-how-lm-works/attention.py")
result = chapter["run_minimal_path"]()
for row in result["context_window"]["rows"]:
    print(row["query_token"], sum(row["attention_weights"]))
    print(row["context_vector"])
```

Each weight row should sum to about 1, and each context vector should have the same dimension as the value vectors. The code uses fixed toy data and no random process, so repeated runs produce identical results.

## 5. Keep the most recent N tokens when the window overflows

```python
import runpy

chapter = runpy.run_path("chapters/stage1-how-lm-works/attention.py")
print(chapter["truncate_to_recent_tokens"](["a", "b", "c", "d", "e"], 3))
print(chapter["run_minimal_path"]()["context_window"]["kept_tokens"])
```

The first line prints `['c', 'd', 'e']`; the second prints `['small', 'models', 'too']`. Truncation happens before attention, so dropped tokens do not appear in the keys, values, or weights.

This example uses single-head full attention without a mask: every query can see every key in its window. Real generative models usually add a causal mask so a position cannot see future tokens, and they use learned projections and multiple attention heads. The `demo_scope` field records these simplifications so the toy calculation is not mistaken for a complete model.

## 6. A context window is not “memory” itself

A context window is the token capacity a model can receive in one forward pass. Making it larger does not automatically mean the model remembers or understands everything; information inside the window still has to be read through attention, and tokens outside it are not visible in that pass.

Model parameters can be viewed as long-term capabilities stored after training, while the current context window is a temporary workspace for this inference step. They are not the same thing. “Keep the most recent N” is only one truncation strategy demonstrated here, not a claim that it fits every task; important instructions, retrieved evidence, or long documents may need other management and summarization methods.
