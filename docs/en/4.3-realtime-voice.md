# 4.3 Realtime Voice: Simulating Session State with Events

## 1. Why realtime voice is not ordinary chat plus TTS

Ordinary chat usually works in complete turns: the user finishes speaking, the system receives the full text, the model answers, and TTS plays the result. Realtime voice is a continuous pipeline: VAD detects speech boundaries, streaming ASR revises the transcript, the dialogue system manages turn state, and response generation can overlap with TTS.

When a user keeps speaking while an answer is playing, barge-in occurs. The system must stop unsent output, clear queued audio, and attach the new transcript to the correct session state. This involves latency, event ordering, and state races; adding TTS to the last step of an ordinary chat does not solve it.

This chapter simulates only text events after ASR. It does not capture sound, run VAD, ASR, or TTS, and does not generate real audio.

## 2. Four events and their state transitions

`RealtimeSession` handles four event types in arrival order:

- `transcript.partial`: replaces the current transcript without generating an answer.
- `transcript.final`: commits the canonical transcript, clears the current text, and queues exactly one deterministic answer.
- `response.create`: moves the oldest pending answer to the emitted list.
- `response.cancel`: discards unsent answers. A supplied `response_id` cancels that answer; otherwise all pending answers are cancelled.

`snapshot()` returns the current transcript, final transcripts, pending answers, emitted answers, cancelled answers, and event log. Answers use increasing identifiers, so the same event sequence always produces the same result. An emitted answer has crossed the send boundary and cannot be recalled by cancellation.

## 3. Run the minimal event stream

From the repository root, run:

```bash
uv sync --frozen
uv run python chapters/stage4-orchestration/realtime_voice.py
```

The example feeds three partial transcripts and then commits a final transcript. `response.create` emits `response-1`. A second final queues `response-2`, and one `response.cancel` discards it. The result contains one emitted answer and one cancelled answer.

## 4. Inspect state changes directly

Pass this code to `uv run python -`:

```python
import runpy

chapter = runpy.run_path("chapters/stage4-orchestration/realtime_voice.py")
session = chapter["RealtimeSession"]()
session.handle({"type": "transcript.partial", "text": "请"})
session.handle({"type": "transcript.partial", "text": "请帮我"})
session.handle({"type": "transcript.final", "text": "请帮我"})
session.handle({"type": "response.create"})
print(session.snapshot()["emitted_responses"])
```

Print `snapshot()` between the two partial events to confirm that no answer is pending. Insert `response.cancel` before `response.create` to confirm that the answer becomes cancelled rather than emitted. The smoke tests cover these boundaries, event ordering, and deterministic repeated runs.

## 5. From simulation to a real system

The teaching state machine deliberately omits real audio-pipeline complexity. A production integration still needs:

- VAD endpointing, acoustic echo cancellation, and noisy-environment handling so the system does not transcribe its own voice.
- Sequenced, timestamped, acknowledged event transport with state recovery after reconnects.
- Streaming generation, TTS playback buffers, and hardware output queues; cancellation must stop generation and drop audio waiting to play.
- Backpressure, timeouts, permissions, log redaction, and metrics for end-to-end latency and barge-in success.

The simulator can validate state transitions, but it cannot prove that a real audio path meets latency or interruption requirements.
