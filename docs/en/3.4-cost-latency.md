# 3.4 Cost and Latency: Caching, Routing, and Simulated Metering

## 1. What this chapter tackles

Every model call consumes input and output tokens and adds waiting time. Repeated requests, overly capable models, and long contexts all increase cost. This chapter uses deterministic simulated data to examine two common controls: caching repeated responses and routing requests of different complexity to different models.

All token counts, prices, and timings are teaching assumptions, not real bills or claims about any provider's current pricing or performance.

## 2. Cache by normalized prompt

`TokenCache` uses the normalized prompt as its key. `normalize_prompt()` applies Unicode NFKC normalization and collapses repeated whitespace, so leading or trailing spaces, tabs, and newlines do not create duplicate entries. Case and punctuation are preserved to avoid merging requests with different meanings.

The first lookup misses and generates a response to store in the cache. A second equivalent lookup hits and reuses that response. The cache also counts hits and misses. A production system must address tenant isolation, sensitive data, expiration, and model or prompt versions; it should not share every response globally by prompt text alone.

## 3. Routing and simulated metering

`ModelRouter` uses a transparent heuristic: it chooses `strong_model` when estimated tokens exceed a threshold or when a complexity marker such as analysis, comparison, or design appears. Short, simple questions use `cheap_model`. The default threshold in this chapter is 20 simulated tokens.

`estimate_tokens()` uses the toy rule of roughly one token per four characters. Cost is the sum of input tokens times the input price and output tokens times the output price, divided by one million. Latency adds a base delay to per-token input and output delays. On a cache hit, this chapter sets simulated generation cost to zero and keeps a small retrieval latency.

## 4. Run the cost and latency experiment

From the repository root, run:

```bash
uv sync --frozen
uv run python chapters/stage3-reliability/cost_latency.py
```

The output contains the first call and cached call for the same arithmetic question. The first call misses and incurs simulated cost. The normalized repeat hits the cache, returns the same response, and reduces both cost and latency. The output also shows a complex architecture question routed to `strong_model`.

## 5. Understand four trade-offs

- Caching: greatly reduces repeated-request cost and latency, but needs memory, invalidation, and isolation; a bad key can leak an answer across requests.
- Routing: uses cheaper models for simple work, but heuristics can misclassify requests; critical tasks need quality evaluation and fallback behavior.
- Batching: combines requests to improve throughput and amortize fixed overhead, but adds waiting time, and one failed item may affect the batch.
- Context compression: summaries or trimming reduce input tokens but can lose constraints, evidence, or details; verify that essential information survives compression.

These controls can be combined. Measure quality, tail latency, memory, and failure rate rather than optimizing only the simulated cost.
