# 2.4 Memory and Context: Keeping Early Key Facts with a Sliding Window

## 1. What this chapter tackles

A model has a limited context window, but a conversation can keep growing. Keeping only the latest messages makes early facts such as time zones, preferences, or constraints disappear. This chapter implements `MemoryStore`: recent messages use a sliding window, evicted messages enter a summary, and the final context is packed under a character budget.

The example records one early key fact and then adds newer messages until that fact leaves the recent window while remaining in the old-message summary.

## 2. Do not confuse three kinds of memory

- Short-term context: the material actually sent to the model for the current request. Here it combines the recent window and the old-message summary.
- Long-term memory: information persisted across sessions, such as a user profile, past decisions, or notes in external storage.
- Retrieval memory: relevant entries selected from a larger memory collection for the current question and then placed in short-term context.

An old-message summary is not automatically long-term memory; it also disappears if the program exits without saving it. Retrieval means “fetch on demand,” not “put all history into the window.”

## 3. Run the key-fact retention experiment

From the repository root, run:

```bash
uv sync --frozen
uv run python chapters/stage2-agent-core/memory.py
```

The window keeps at most 3 messages. After 6 messages are added, the earliest 3 have slid out, including `KEY_FACT`. Inspect the window and summary:

```python
import runpy

chapter = runpy.run_path("chapters/stage2-agent-core/memory.py")
result = chapter["run_minimal_path"]()
print("In recent window:", result["window_contains_key_fact"])
print("In old summary:", result["summary_contains_key_fact"])
print(result["snapshot"]["context"])
```

The output is `In recent window: False` and `In old summary: True`. `evicted_messages` also keeps original copies of evicted messages so the sliding process is visible.

## 4. Approximate a token budget with characters

This chapter does not depend on a model tokenizer. It uses the rough estimate that 4 characters are about 1 token. Actual token counts vary with language, whitespace, and the tokenizer, so `approximate_tokens` is only for teaching.

`char_budget` is a hard limit on the context string. `build_context()` starts with the summary and recent messages; if they exceed the budget, it drops the oldest text from the left and keeps the newer ending, so the result may start with `...`. `snapshot()` reports character count, estimated tokens, and whether truncation occurred.

## 5. Summaries always lose information

The summary here is deterministic, lossy compression: whitespace in old messages is collapsed, and each message keeps at most its first 80 characters, with excess text replaced by `...`. Real systems may use a model to rewrite or merge messages, making omitted details or changed meanings even more likely.

A summary is therefore useful as rough background, not as storage for data that must be checked word for word. Important facts should be structured separately and retrieved when needed. Also watch for errors in a summary being repeated as if they were facts.

## 6. Inspect the window and budget yourself

Create `MemoryStore(max_messages=2, char_budget=30)`, add one long message, and inspect the length of `build_context()`. Change `max_messages` to 1 and watch more messages enter the summary.
