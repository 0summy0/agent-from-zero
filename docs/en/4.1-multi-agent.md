# 4.1 Multi-Agent Collaboration: Writer, Critic, and Bounded Orchestration

## 1. What this chapter tackles

A task that one Agent can finish does not automatically benefit from being split among several Agents. Multi-agent systems are not better by default: separation helps only when role boundaries are clear, independent review can really reduce mistakes, or different steps need different tools and context.

This chapter implements a deterministic Writer/Critic/Orchestrator teaching pipeline. It does not call a language model. Fixed rules generate a short answer, check required points, and control revision, so the whole path runs repeatedly offline on a CPU.

## 2. What the three roles do

- Writer: generates a short draft from the user's request. The toy Writer includes one locally supported point in its first draft and, after Critic feedback, adds at most one missing point during revision.
- Critic: independently checks the draft against `required_points`, then reports whether it passes, which points are missing, and what to revise. Coverage checking does not prove factual correctness.
- Orchestrator: keeps the original draft, calls Critic, decides whether to revise or stop, and returns the latest answer.

Role separation can decouple generation from checking, and independent review may catch constraints that a single Agent missed. The costs include longer serial waits, more model calls and tokens, and error propagation: one role's mistakes enter the next role's context. Roles can also share the same blind spot, so a majority vote is not a quality guarantee.

## 3. Define termination conditions first

A loop without termination conditions keeps consuming latency and cost. This chapter has two explicit stop conditions: Critic confirms that every required point is covered, or the check count reaches `MAX_ROUNDS = 2`. One revision is allowed after the first failed check; if the second check still fails, the current best result and its unmet status are returned.

`rounds` counts Critic checks, not revisions. A first-pass result therefore has `rounds` equal to 1, while a result after one revision has `rounds` equal to 2. Production systems should also add time or token budgets, tool-failure limits, human takeover, and safe fallbacks. Reaching a limit must never be reported as success.

## 4. Run the minimal collaboration path

From the repository root, run:

```bash
uv sync --frozen
uv run python chapters/stage4-orchestration/multi_agent.py
```

The default request contains two required points: role separation and independent review. The first draft contains only the first point, and Critic asks for the missing one. After one Writer revision, the second check passes. The program uses only the Python standard library, with no network, GPU, API key, or random sampling.

## 5. Read the result

`run_minimal_path()` returns four fields: `draft` is the initial draft, `critique` is the final check, `final` is the latest answer, and `rounds` is the number of checks. When `critique["satisfied"]` is `false`, the result is not marked as passing even if the round limit has been reached.

The toy Critic only matches required-point substrings. That is useful for exposing orchestration flow, but it cannot replace semantic evaluation, factual verification, or security auditing. A request must contain the “要点：” marker unless `required_points` is supplied explicitly; empty requests and empty point lists are rejected.

## 6. Inspect revision and the round limit

Pass this code to `uv run python -`:

```python
import runpy

chapter = runpy.run_path("chapters/stage4-orchestration/multi_agent.py")
result = chapter["run_minimal_path"]()
print(result["draft"])
print(result["critique"])
print(result["final"])
print(result["rounds"])

capped = chapter["run_minimal_path"](
    "请说明三个要点。",
    ["角色分工", "独立检查", "终止条件"],
)
print(capped["rounds"])
print(capped["critique"]["satisfied"])
```

The default result shows one revision and two checks. The three-point example allows only one revision, so it stops at the second check and explicitly reports that the termination-condition point is still missing. Smoke tests cover one revision, no revision, the round limit, empty-input rejection, deterministic results, and JSON output.
