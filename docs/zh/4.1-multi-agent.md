# 4.1 多智能体协作：Writer、Critic 与有界编排

## 1. 这一章要解决什么

一个 Agent 能完成的任务，不一定要拆给多个 Agent。多智能体不是默认更好的方案：只有当角色边界清晰、独立检查确实能减少错误，或者不同步骤需要不同工具与上下文时，拆分才有价值。

本章实现一个确定性的 Writer/Critic/Orchestrator 教学链路。它不调用大模型，只用固定规则生成短答案、检查要点并控制修订，因此可以在 CPU 上离线重复运行。

## 2. 三个角色各做什么

- Writer：根据用户要求生成简短草稿。本章的玩具 Writer 第一次只写一个本地支持要点，收到 Critic 反馈后最多补充一个遗漏要点。
- Critic：独立对照 `required_points` 检查草稿，返回是否满足、遗漏要点和修订反馈。它检查的是覆盖率，不等于证明事实正确。
- Orchestrator：保存原始草稿，调用 Critic，决定继续修订还是终止，并返回最后一份答案。

角色分工适合把生成与检查解耦，独立检查也可能发现单 Agent 遗漏的约束。但代价包括更长的串行等待、更多模型调用与 token 成本，以及错误传播：前一个角色的错误会进入下一个角色的上下文。多个角色也可能共享同一种盲区，所以不能把“多数同意”当成质量保证。

## 3. 必须先定义终止条件

没有终止条件的循环会持续消耗延迟和成本。本章采用两个明确的停止条件：Critic 确认全部要点已覆盖，或者检查轮数达到 `MAX_ROUNDS = 2`。第一轮不通过时允许一次修订，第二轮仍不通过就返回当前最佳结果和未满足状态。

`rounds` 表示 Critic 检查的次数，不是修订次数。因此一次通过时 `rounds` 为 1，经过一次修订后为 2。生产系统还应加入时间或 token 预算、工具失败上限、人工接管与安全回退；达到上限时不能假装任务已经成功。

## 4. 运行最小协作链路

在仓库根目录执行：

```bash
uv sync --frozen
uv run python chapters/stage4-orchestration/multi_agent.py
```

默认请求包含“角色分工”和“独立检查”两个要点。首轮草稿只有第一个要点，Critic 要求补充；Writer 修订一次后，第二轮检查通过。程序只使用 Python 标准库，无网络、GPU、API key 或随机采样。

## 5. 读懂返回结果

`run_minimal_path()` 返回四个字段：`draft` 是最初草稿，`critique` 是最后一轮检查，`final` 是最后一份答案，`rounds` 是检查轮数。`critique["satisfied"]` 为 `false` 时，即使已到轮数上限，也不会把结果标记为通过。

这个玩具 Critic 只做要点子串匹配，适合暴露编排流程，不能替代语义评测、事实验证或安全审计。输入必须包含“要点：”标记，也可以显式传入 `required_points`；空请求和空要点列表会被拒绝。

## 6. 亲手检查修订与上限

把下面代码交给 `uv run python -` 执行：

```python
import runpy

chapter = runpy.run_path("chapters/stage4-orchestration/multi_agent.py")
result = chapter["run_minimal_path"]()
print(result["draft"])
print(result["critique"])
print(result["final"])
print(result["rounds"])

capped = chapter["run_minimal_path"](
    "请说明三个要点。",
    ["角色分工", "独立检查", "终止条件"],
)
print(capped["rounds"])
print(capped["critique"]["satisfied"])
```

默认结果应显示一次修订和两轮检查。三个要点的例子只能完成一次修订，因此仍在第二轮停止，并明确报告“终止条件”缺失。冒烟测试覆盖一次修订、无需修订、轮数上限、空输入拒绝、结果确定性和 JSON 输出。
