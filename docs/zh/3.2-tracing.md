# 3.2 追踪：用 JSONL 调用链调试 Agent

## 1. 这一章要解决什么

Agent 出错时，仅看最后一条错误日志通常不够：你需要知道它之前做了什么、哪个工具最慢，以及失败发生在调用链的哪一层。

本章实现一个极简追踪器，用四个嵌套或关联的 span 记录一次 toy Agent 运行。全部数据写入本地 JSONL 文件，无需网络、GPU 或 API。

## 2. trace 与 log 的区别

log 通常是按时间到达的离散事件，例如“开始查询”和“查询结束”。trace 则用 `span_id` 与 `parent_span_id` 表达因果关系，把一次任务中的规划、工具调用和回答组织成树。

每条 span 记录名称、起止时间、毫秒耗时和属性。多个 span 可以拥有同一个父 span，因此调用链不一定是简单的单链，也可以有分支。

`TraceWriter.span()` 是上下文管理器：正常退出时写入 `ok`，抛出异常时写入 `error` 和错误消息，然后继续向上传播。耗时按结束时间减开始时间计算，并限制为非负数。

## 3. 跑通最小追踪

在仓库根目录执行：

```bash
uv run python chapters/stage3-reliability/tracing.py
```

`run_minimal_path()` 在临时目录创建 `trace.jsonl`，运行四道固定步骤后返回 span 数量和关键 span。临时目录会自动清理，返回结果只包含可序列化的摘要。

关键 span 包括 `agent.run`、`tool.lookup` 和 `agent.answer`；完整文件还包含 `agent.plan`。固定时钟让示例中的时间与耗时可重复。

## 4. 为什么 Agent 调试需要完整调用链

假设最终回答错误，完整 trace 能帮助你区分：规划选错了步骤、工具返回了坏数据、模型误读了工具结果，还是答案合成出了问题。

父 span 的耗时包含子 span 的耗时，所以可以沿着树定位瓶颈。异常属性会保留失败层级，避免只能看到最外层错误。跨进程追踪时，还可以把 trace 与 span 关联 ID 一起写入日志。

隐私方面，不要把密钥、完整用户敏感信息或不必要的大段工具输出直接放进 attributes。生产系统还需要采样、保留期限和访问控制。

## 5. 亲手检查调用链

把下面代码交给 `uv run python -` 执行：

```python
import json
import runpy
import tempfile
from pathlib import Path

chapter = runpy.run_path("chapters/stage3-reliability/tracing.py")
with tempfile.TemporaryDirectory() as directory:
    result = chapter["ToyAgentRunner"](directory, clock=lambda: 1.0).run("What is 2 + 2?")
    path = Path(directory) / "trace.jsonl"
    records = [json.loads(line) for line in path.read_text(encoding="utf-8").splitlines()]
print(result["span_count"])
print([(record["name"], record["parent_span_id"]) for record in records])
```

冒烟测试覆盖父子关系、非负耗时、JSONL 逐行解析、异常 span 记录、临时目录输出和固定时钟下的确定性。测试用假时钟避免真实等待。
