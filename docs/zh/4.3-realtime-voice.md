# 4.3 实时语音：用事件流模拟会话状态

## 1. 为什么实时语音不是普通 chat 加 TTS

普通聊天通常按完整轮次工作：用户说完，系统收到完整文本，模型生成回答，再用 TTS 播放。实时语音则是一条持续运行的流水线：VAD 判断说话起停，流式 ASR 不断更新转写，对话系统管理轮次状态，回答与 TTS 可以流式进行。

用户在新回答播放时继续说话，就会发生打断（barge-in）。系统必须停止尚未发出的回答、清理待播放音频，并把新转写带入正确的会话状态。这里既有延迟问题，也有事件顺序和状态竞争问题，不是给普通 chat 的最后一步加一个 TTS 就能解决。

本章只模拟 ASR 之后的文本事件，不采集声音，不运行 VAD、ASR 或 TTS，也不生成真实音频。

## 2. 四个事件与状态转换

`RealtimeSession` 按到达顺序处理四类事件：

- `transcript.partial`：用最新文本替换当前转写，不生成回答。
- `transcript.final`：提交 canonical 转写，清空当前转写，并恰好排队一个确定性回答。
- `response.create`：取出最早的一个待发回答，移到已发列表。
- `response.cancel`：丢弃尚未发出的回答；指定 `response_id` 时只取消该回答，否则取消全部待发回答。

`snapshot()` 返回当前转写、最终转写、待发回答、已发回答、已取消回答和事件日志。回答使用递增编号，因此相同事件序列总产生相同结果。已发回答代表越过了发送边界，取消不能把它撤回。

## 3. 运行最小事件流

在仓库根目录执行：

```bash
uv sync --frozen
uv run python chapters/stage4-orchestration/realtime_voice.py
```

示例先输入三段 partial 转写，再提交 final；`response.create` 发出 `response-1`。第二个 final 排队 `response-2`，随后一次 `response.cancel` 丢弃它。最终只有一条已发回答和一条已取消回答。

## 4. 亲手观察状态变化

把下面代码交给 `uv run python -` 执行：

```python
import runpy

chapter = runpy.run_path("chapters/stage4-orchestration/realtime_voice.py")
session = chapter["RealtimeSession"]()
session.handle({"type": "transcript.partial", "text": "请"})
session.handle({"type": "transcript.partial", "text": "请帮我"})
session.handle({"type": "transcript.final", "text": "请帮我"})
session.handle({"type": "response.create"})
print(session.snapshot()["emitted_responses"])
```

可以在两次 partial 之间打印 `snapshot()`，确认待发回答仍为空；也可以在 `response.create` 之前插入 `response.cancel`，确认回答进入已取消列表而不是已发列表。冒烟测试覆盖这些边界、事件顺序和重复运行的确定性。

## 5. 从模拟走向真实系统

教学状态机故意省略了真实音频管道的复杂度。接入生产系统时还需要处理：

- VAD 的端点检测、回声消除和噪声环境，避免系统把自己的声音再次转写。
- 带序号、时间戳和确认机制的事件传输，以及网络重连后的状态恢复。
- 流式回答、TTS 播放缓冲和硬件输出队列；取消时要停止生成并丢弃待播放音频。
- 背压、超时、权限、日志脱敏，以及端到端延迟和打断成功率指标。

模拟器能验证状态转换，却不能证明真实音频链路满足延迟或打断要求。
