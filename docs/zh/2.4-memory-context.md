# 2.4 记忆与上下文：滑动窗口如何保留早期关键事实

## 1. 这一章要解决什么

模型能看到的上下文长度有限，对话却可能不断增加。如果只保留最近几条消息，早期的时区、偏好或约束就会消失。本章实现 `MemoryStore`：最近消息使用滑动窗口，滑出窗口的旧消息进入摘要，最后再按字符预算组装上下文。

示例先记录一条早期关键事实，再加入多条新消息，让这条事实滑出最近窗口，同时仍保留在旧消息摘要中。

## 2. 三种记忆不要混为一谈

- 短期上下文：本次请求实际送给模型的内容。本章由最近窗口和旧消息摘要共同组成。
- 长期记忆：跨会话保存的信息，例如用户档案、历史决定或外部存储中的笔记。
- 检索记忆：根据当前问题从较大的记忆集合中找出相关条目，再放入短期上下文。

旧消息摘要本身不等于长期记忆；如果程序退出后不保存，它也会消失。检索是“按需取回”，也不是“把所有历史都塞进窗口”。

## 3. 跑通关键事实保留实验

在仓库根目录执行：

```bash
uv sync --frozen
uv run python chapters/stage2-agent-core/memory.py
```

窗口最多保留 3 条消息。加入 6 条消息后，最早的 3 条已经滑出窗口，其中包含 `KEY_FACT`。检查窗口和摘要：

```python
import runpy

chapter = runpy.run_path("chapters/stage2-agent-core/memory.py")
result = chapter["run_minimal_path"]()
print("In recent window:", result["window_contains_key_fact"])
print("In old summary:", result["summary_contains_key_fact"])
print(result["snapshot"]["context"])
```

输出应为 `In recent window: False` 和 `In old summary: True`。`evicted_messages` 还保留了被滑出消息的原始副本，便于观察滑动过程。

## 4. 用字符数近似 token 预算

本章不依赖模型 tokenizer，而是用 4 个字符约等于 1 个 token 的粗粒度估算。真正的 token 数会随语言、空格和 tokenizer 变化，所以 `approximate_tokens` 只能用于教学。

`char_budget` 是上下文字符串的硬上限。`build_context()` 先放摘要和最近消息；如果超预算，就从左侧丢弃最旧文本，并保留较新的结尾，因此结果可能以 `...` 开头。`snapshot()` 会报告字符数、估算 token 数和是否发生截断。

这是教学简化：从左侧截断可能把开头的 system 指令一起删掉。真实系统通常把 system prompt 固定在预算之外，先为它保留空间，再分配工具输出、检索结果和最近对话的预算。不要让模型生成的历史内容挤掉系统约束。

## 5. 摘要一定会丢信息

本章的摘要是确定性的有损压缩：旧消息会先合并空白，每条内容最多保留前 80 个字符，超出部分变成 `...`。真实系统可能使用模型改写或合并多条消息，更容易遗漏细节或改变含义。

因此，摘要适合提供粗略背景，不适合保存需要逐字核对的数据。重要事实应另行结构化保存，并在需要时检索；同时要警惕摘要中的错误被当成事实继续传播。

## 6. 亲手检查窗口与预算

创建 `MemoryStore(max_messages=2, char_budget=30)`，加入一条长消息，再检查 `build_context()` 的长度。把 `max_messages` 改成 1，观察更多消息进入摘要。
