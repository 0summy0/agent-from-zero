# 1.1 Tokenizer：看见模型怎样切分中文

## 1. 这一章要解决什么

语言模型看到的并不是我们眼中的“字”和“词”，而是一串 token 编号。本章不训练模型，也不下载模型权重，只取 Qwen2.5-0.5B-Instruct 的 `tokenizer.json`，亲手把一句中英对照文本变成 token。你需要一个能运行 Python 的 CPU 环境；首次运行需要下载约 6.8 MB 的分词文件，不需要 API key。

## 2. Token 到底是什么

Token 是分词器根据词表切出的文本单位。它可能是一个常见词、一个单字、一个词的一部分，也可能是带着前导空格的英文片段。不要背“一个汉字等于一个 token”或“一个英文单词等于一个 token”这样的规则：词表不同，结果就可能不同。

模型上下文窗口计算的是 token 数，而不是我们平常说的字数。相同意思被切得越碎，占用的上下文位置通常越多，处理成本也可能随之增加。不过，token 多并不直接等于回答差，切分数量与答案质量不能混为一谈。

## 3. 跑通第一个实验

在仓库根目录执行下面两条命令。第一条安装锁定依赖，第二条读取分词文件并编码中英文样本：

```bash
uv sync --frozen
HF_ENDPOINT=https://hf-mirror.com uv run python chapters/stage1-how-lm-works/tokenizer.py
```

程序优先使用 `HF_ENDPOINT` 指定的 Hugging Face 端点。本次执行机器上镜像返回 403，因此代码还提供了同一 Qwen 模型的 ModelScope 文件地址作为回退；也可以用 `TOKENIZER_URL` 显式指定文件地址。文件下载后会缓存，之后运行不再重复下载。整个实验只加载 tokenizer，不加载 0.5B 模型权重，也不需要 PyTorch。

## 4. 读懂这次切分

本次实测使用同一份 Qwen tokenizer，结果如下。英文片段中的前导空格是有意义的，它表示这个 token 与前面的文本边界有关。

| 样本 | 字符数 | 可读 token 片段 | token 数 |
|---|---:|---|---:|
| 中文：`智能体现在会调用工具` | 10 | `智能`、`体现在`、`会`、`调`、`用`、`工具` | 6 |
| 英文：`Agents can call tools now` | 25 | `Agents`、` can`、` call`、` tools`、` now` | 5 |

“调用”在这里没有成为一个 token，而是拆成了“调”和“用”；“智能”和“工具”则各自完整保留。这就是“中文被切碎”最直观的样子：常用片段可能被合并，另一些我们认为自然的词仍会拆开。这个样本里中文比英文多 1 个 token，但不能据此推断所有中文都更费 token；换一段文本或换一个 tokenizer，比例都可能改变。

## 5. 亲手检查返回结构

仍在仓库根目录，把下面的 Python 代码交给 `uv run python -` 执行，或在 Python 交互环境中逐行运行。`runpy.run_path` 让我们直接加载带连字符目录中的章模块，返回字典则与冒烟测试共用同一条最小路径。

```python
import runpy

chapter = runpy.run_path("chapters/stage1-how-lm-works/tokenizer.py")
result = chapter["run_minimal_path"]()
print(result["chinese"]["tokens"])
print(result["chinese"]["token_count"])
print(result["english"]["tokens"])
print(result["english"]["token_count"])
```

测试不会要求每次生成的 token 文本恰好等于某段硬编码字符串，而是校验 `chapter`、`model`、`chinese`、`english` 等字段及其类型，再检查 token 数与 ID 列表长度一致。这样可以抓住返回结构被破坏的问题，同时给分词器实现保留合理变化空间。
