# 3.4 成本与延迟：缓存、路由与模拟计量

## 1. 这一章要解决什么

Agent 的每次模型调用都会消耗输入和输出 token，并引入等待时间。重复请求、过难模型和过长上下文都会推高成本。本章用确定性的模拟数据，观察两种常用控制手段：缓存重复响应，以及把不同复杂度请求路由到不同模型。

所有 token 数、单价和延迟都是教学假设，不是真实账单，也不代表任何服务商的当前价格或性能。

## 2. 用规范化 prompt 做缓存键

`TokenCache` 用规范化后的 prompt 作为键。`normalize_prompt()` 做 Unicode NFKC 规范化并合并连续空白，因此行首行尾空格、制表符和换行不会产生重复条目；大小写和标点保留，避免把语义不同的请求误合并。

第一次查询未命中，需要生成响应并写入缓存；第二次等价查询命中，可以直接复用响应。缓存还统计命中数和未命中数。生产系统必须进一步考虑租户隔离、敏感数据、过期时间和模型或提示版本，不能只凭 prompt 文本全局共享。

## 3. 路由与模拟计量

`ModelRouter` 使用透明的启发式规则：预估 token 数超过阈值，或者出现分析、比较、设计等复杂度标记时，选择 `strong_model`；短而简单的问题选择 `cheap_model`。本章默认阈值为 20 个模拟 token。

`estimate_tokens()` 用“约四个字符一个 token”的玩具规则计数。成本按输入 token 数乘输入单价、加输出 token 数乘输出单价，再除以一百万计算；延迟由基础延迟和输入、输出的每 token 延迟相加。缓存命中时，本章将模拟生成成本设为零，只保留很小的读取延迟。

## 4. 运行成本与延迟实验

在仓库根目录执行：

```bash
uv sync --frozen
uv run python chapters/stage3-reliability/cost_latency.py
```

输出包含同一算术问题的首次调用和缓存调用。首次调用未命中并产生模拟成本；规范化后的重复请求命中缓存，响应相同，但成本和延迟下降。输出还展示一个复杂架构问题被路由到 `strong_model`。

## 5. 理解四种手段的权衡

- 缓存：能显著降低重复请求的成本和延迟，但需要内存、处理失效与隔离；错误键还可能串用答案。
- 路由：让简单问题使用便宜模型，但启发式可能误判；关键任务需要质量评估和回退机制。
- 批处理：把多个请求合并可提高吞吐、摊薄固定开销，但会增加等待时间；一个失败项也可能影响同批结果。
- 上下文压缩：摘要或裁剪能减少输入 token，却可能丢失约束、证据或细节；压缩后应验证关键信息仍完整。

这些手段可以组合，但要同时观察质量、尾延迟、内存和失败率，不能只追求最低模拟成本。

把下面代码交给 `uv run python -` 执行：

```python
import runpy

chapter = runpy.run_path("chapters/stage3-reliability/cost_latency.py")
result = chapter["run_minimal_path"]()
print(result["first_call"])
print(result["cached_call"])
print(result["routing_example"])
```

冒烟测试覆盖缓存命中、键归一化、未命中、路由规则、成本与延迟计算，以及结果确定性。请记住，这里的数字仅用于解释公式，不能作为容量规划或真实账单的依据。
